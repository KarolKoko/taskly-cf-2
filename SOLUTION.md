## Solution for taskly-cf

Prezentacja modułowego agenta AI do uzupełniania testów jednostkowych dla aplikacji TO-DO. Ze względu na małą ilość czasu który mogłem przeznaczyć na wykonanie zadania, pozwoliłem sobie skorzystać z deweloperskich narzędzi AI do generowania kodu. Uważam jednak że to słuszna decyzja, ponieważ Agentic Engineering jest już na tyle mocno rozwinięty, że pozwala diametralnie przyspieszyć pracę.

### The main technical decisions and their rationale:
Zdeycdowałem się na implementację własnego Agentic Workflow, który uruchamiany jest w GH Actions. Moją motywacją było bezpieczeństwo i ograniczenie roli LLM w bezpośredniej interakcji z kodem. Generowany kod testów jednostkowych nie nadaje się już do ponownego testowania, więc Model LLM pełni funkcję doradcy. Moduł do generowania kodu testów jednostkowych jest natywnie zaimplementowany w aplikacji w katalogu /generator. Unikalność rozwiązania polega na rozddzieleniu roli generatora kodu i doradcy LLM. Dodatkowa zaleta takiego rozwiązania polega na ograniczeniu zuzycia kredytów, a co za tym idzie kosztów utrzymania repozytorium. Jeżeli chodzi o wskazówki dla agenta, to zostały one umieszczone w katalogu agents zgodnie z najlepszymi praktykami. Jako model doradczy wybrałem gpt-5.5, lecz nie jest sztywno ustalone jaki model musi być użyty do tego zadania. Niewątpliwą zaletą zastosowanego przeze mnie rozwiązania jest możliwość modyfikacji patternów testowych bez zmieniania instrukcji agentów. Generator interpretuje odpowiedź LLM i n podstawie tego pisze testy. Jest to podporządkowane deweloperowi, rezultat zawsze będzie mieścił się w narzuconych ramach. Głownym źródłem dla LLM jest scrapowana dokumentacja API vitest - jest to niezależne od zdalnego źródła, a dodatkowo dokumentacja w JSON jest niezmienna, dopóki ktoś jej nie zaktualizuje. Workflow wypycha nowo stworzone testy na repozytorium, a następnie wykonuje je. W przypdaku błędu dodawany jest nowy issue do GH.

### How to run the PR workflow and which prerequisites must be met:
Workflow rozpoczyna się wraz z żądaniem pull request. Porównywany jest wtedy kod, a następnie rusza złożony pipieline. Przede wszystkim jeśli chcemy skorzystać z generatora potrzebny jest nam klucz OpenAI. Przed właściwym generowaniem testów, uruchamiany jest pre-check, który waliduje składnię i pliki .env. Flow jest taki: PR → baseline checks → generator (diff → skille → plan JSON → render) → testy w izolacji → PASS: commit do PR / FAIL: issue GH → końcowy komentarz w PR.
